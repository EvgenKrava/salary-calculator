# Infrastructure App Layer (Terraform) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax. NOTE: this is infrastructure — there is no red-green TDD. Each task's verification is `terraform fmt -check -recursive` + `terraform validate` (via `terraform init -backend=false`, which needs no AWS credentials). **`terraform apply` is the USER's action** — it creates real, billable resources — and is never run by an implementer.

**Goal:** Make the API reachable and the frontend hostable: package the Lambdas, expose the API behind API Gateway with a Cognito JWT authorizer, create the Cognito user pool and its three groups, host the SPA on S3 + CloudFront, provision the documents bucket that will trigger extraction, and add a migration Lambda that applies the schema over the Data API.

**Architecture:** Extends the existing `infra/` stack (state bootstrap, VPC, Aurora Serverless v2 + Data API + Secrets Manager — already merged). Lambdas are built with **esbuild** into single-file bundles and zipped by Terraform's `archive_file`; no container images. All Lambdas reach Aurora over the **RDS Data API**, so none are attached to the VPC. The extraction Lambda's AWS resources (S3 notification, IAM for Bedrock, the function itself) are owned by **this plan** against a documented handler contract, so the concurrently-developed extraction application code has no Terraform to write.

**Tech Stack:** Terraform ~> 1.10 (installed: v1.15.8), AWS provider ~> 5.x, esbuild, AWS profile `yevhenii`.

## Global Constraints

- **AWS profile `yevhenii`** for all AWS access; provider already sets `profile = var.aws_profile`.
- **Terraform** `>= 1.10` (the stack uses `use_lockfile`); **AWS provider** `~> 5.0`, already pinned.
- **Never run `terraform apply` or `terraform plan`.** Only `fmt`, `init -backend=false`, `validate`.
- **Reuse the existing conventions:** every resource name prefixed `${var.project_name}`, `default_tags` from the provider, and outputs added to the existing `infra/outputs.tf`.
- **Do not edit** `infra/database.tf`, `infra/network.tf`, `infra/versions.tf`, or `infra/bootstrap/` except where a task explicitly says so. Those are merged and reviewed.
- **No secrets in code.** The Bedrock bearer token is passed as a Lambda env var sourced from a Terraform variable marked `sensitive = true`, supplied via `terraform.tfvars` (gitignored).
- **Handler contract is load-bearing.** The extraction Lambda's handler path and env vars are defined in Task 5 and must match what the extraction plan builds. Both plans reference the same contract; do not change it unilaterally.

- [ ] **Step 2: Write the migration handler**

`packages/api/src/migrationHandler.ts`:
```ts
import { RDSDataClient, ExecuteStatementCommand } from '@aws-sdk/client-rds-data';
import { MIGRATIONS } from '@salary/core/migrations';
import { readEnvConfig } from './db/prodDb';

/**
 * Apply every migration in order over the RDS Data API.
 *
 * Invoked on demand (not on a schedule) after the cluster is provisioned and after any
 * schema change. Migrations are not tracked in a journal table yet: 0001 and 0002 are not
 * idempotent (they CREATE and ALTER unconditionally), so re-running a already-applied
 * migration fails loudly rather than corrupting anything. That is the intended behaviour
 * for now — a journal table is a follow-up, not a silent re-run.
 */
export async function handler(): Promise<{ applied: number; errors: string[] }> {
  const config = readEnvConfig(process.env);
  const client = new RDSDataClient({ region: config.region });
  const errors: string[] = [];
  let applied = 0;

  for (const [index, sql] of MIGRATIONS.entries()) {
    try {
      await client.send(
        new ExecuteStatementCommand({
          resourceArn: config.resourceArn,
          secretArn: config.secretArn,
          database: config.dbName,
          sql,
        }),
      );
      applied += 1;
    } catch (err) {
      errors.push(`migration ${index + 1}: ${(err as Error).message}`);
      break; // stop at the first failure — later migrations assume earlier ones applied
    }
  }

  return { applied, errors };
}
```

Note: the Data API's `ExecuteStatement` runs one statement per call in some configurations. If a multi-statement migration is rejected at apply time, the fix is to split each migration file on `;` and send the statements individually — record that as a concern rather than pre-emptively splitting (the SQL contains `;` inside a `CHECK` expression, so naive splitting is wrong).

# Extraction Lambda — deployment contract

Terraform (`infra/extraction.tf`) owns this function's AWS resources; the
`@salary/extraction` package owns its code. This file is the interface between them —
**change it in both plans or not at all.**

## Bundle

| | |
|---|---|
| Build command | `pnpm --filter @salary/extraction bundle` |
| Bundle path | `packages/extraction/dist/extract.js` |
| Lambda handler | `extract.handler` |
| Runtime | `nodejs20.x` |
| Timeout | 300s (vision on a multi-page PDF is slow) |
| Memory | 1024 MB |

## Trigger

An S3 `ObjectCreated:*` notification on the documents bucket, filtered to the `uploads/`
key prefix. The handler receives a standard `S3Event`.

Key convention the uploader must follow:

```
uploads/<docType>/<uuid>-<original-filename>
```

`<docType>` is `revenue` or `schedule` — it tells the extractor which schema to request
without a database round trip.

## Environment variables

| Name | Purpose |
|---|---|
| `AWS_REGION_NAME` | Region (`AWS_REGION` is reserved by the runtime and set automatically) |
| `DB_RESOURCE_ARN` | Aurora cluster ARN, for the RDS Data API |
| `DB_SECRET_ARN` | Secrets Manager ARN holding the DB credentials |
| `DB_NAME` | Database name |
| `DOCUMENTS_BUCKET` | The bucket the object was uploaded to |
| `AWS_BEARER_TOKEN_BEDROCK` | Bedrock API key for the Anthropic SDK |
| `BEDROCK_MODEL_ID` | Defaults to `anthropic.claude-opus-5` |
| `CONFIDENCE_THRESHOLD` | At or above this, stage as approved; below, queue for review |

## IAM already granted

`s3:GetObject` on the documents bucket, `bedrock:InvokeModel` on `anthropic.*` models,
RDS Data API + Secrets Manager on the one cluster, and CloudWatch Logs. The handler needs
no other AWS permission — if it does, that is a contract change.

## Expected behaviour

Write an `extraction_jobs` row for every invocation, including failures, so nothing is
silently dropped. A Bedrock refusal (`stop_reason: 'refusal'`) is a `rejected` job, not a
crash.
```

## Deploying the application

Run these after the infrastructure `apply` from the first-time setup above.

1. **Build the Lambda bundles** (Terraform packages pre-built files):
   ```bash
   ./infra/build/build.sh
   ```
2. **Supply the Bedrock token.** Add to `terraform.tfvars` (gitignored):
   ```hcl
   bedrock_bearer_token = "<Bedrock API key>"
   ```
   Or export `TF_VAR_bedrock_bearer_token`. Without it the extraction Lambda deploys but
   every Bedrock call fails with an auth error.
3. **Apply**, then create the schema — this is a one-time step per database:
   ```bash
   terraform apply
   aws lambda invoke --profile yevhenii \
     --function-name "$(terraform output -raw migrate_function_name)" /dev/stdout
   ```
   A successful response reports `{"applied":3,"errors":[]}`. **Do not re-invoke it** —
   the migrations are not idempotent and a second run fails on the already-created objects.
4. **Smoke-test the API and the Data API path in one call:**
   ```bash
   curl "$(terraform output -raw api_url)/health"
   ```
   `{"status":"ok"}` means the Lambda, the gateway, and the bundle are wired correctly. Then
   confirm the Data API premise (the whole reason no Lambda is in the VPC):
   ```bash
   aws rds-data execute-statement --profile yevhenii \
     --resource-arn "$(terraform output -raw db_cluster_arn)" \
     --secret-arn   "$(terraform output -raw db_secret_arn)" \
     --database     "$(terraform output -raw db_name)" \
     --sql "SELECT count(*) FROM levels"
   ```
5. **Create the first admin user** (there is no public sign-up):
   ```bash
   POOL=$(terraform output -raw cognito_user_pool_id)
   aws cognito-idp admin-create-user --profile yevhenii \
     --user-pool-id "$POOL" --username you@example.com
   aws cognito-idp admin-add-user-to-group --profile yevhenii \
     --user-pool-id "$POOL" --username you@example.com --group-name admin
   ```
6. **Deploy the frontend** once it is built:
   ```bash
   aws s3 sync apps/web/dist "s3://$(terraform output -raw frontend_bucket)/" --delete --profile yevhenii
   aws cloudfront create-invalidation --profile yevhenii \
     --distribution-id "$(terraform output -raw cloudfront_distribution_id)" --paths '/*'
   ```

### Cost note

CloudFront and S3 are pennies at this scale; the standing cost is Aurora Serverless v2. At
`db_min_acu = 0.5` the cluster never scales to zero — setting `db_min_acu = 0` enables
auto-pause on the resolved 15.10+ engine and is recommended for a dev deployment.
```

## Self-Review

**Spec coverage (design §7):**
- Single API Lambda behind API Gateway HTTP API with a Cognito JWT authorizer → Tasks 2, 4.
- Cognito user pool with three groups, employees linked by `cognito_sub` → Task 3.
- SPA on S3 + CloudFront with SPA routing → Task 5 (private bucket + OAC + 403/404 → index.html).
- Two buckets (frontend assets, uploaded documents) → Task 5.
- Extraction Lambda triggered by S3 put events → Task 5, against the Task 5 contract.
- Data API access, no Lambda in the VPC → Task 2 (`local.db_env`, no `vpc_config` anywhere).
- Terraform for everything → all tasks; `apply` remains the user's action.
- Schema application → Task 1 (handler) + Task 2 (function) + Task 6 (runbook invoke).

**Placeholder scan:** No TBD/TODO. Three contingencies are explicit and bounded: the
intermediate `validate` failures in Tasks 2–4 (with the pass required at Task 5), the
Data API multi-statement possibility, and the `AWS_REGION` reserved-name note — each says
what to do and what to report rather than leaving a decision open.

**Consistency:** every resource is `${var.project_name}`-prefixed; the Cognito group names
match `requireRole()` in the API's auth middleware; the extraction env vars match the
contract exactly; `local.db_env` is the single definition of Data API wiring so no Lambda
can drift into needing VPC access.

**Known limitation (deliberate):** migrations have no journal table, so re-invoking the
migration Lambda fails on already-applied objects. That is loud rather than silent, and the
runbook says so — a journal is a follow-up, not a hidden gap.
